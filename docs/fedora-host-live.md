# The host works end to end — FED-HOST-E001

2026-11-08. **The iPad displayed frames HASHI generated from a real Linux
virtual monitor, and touches on its screen moved the Linux pointer.** This is
the first time the host has run at all, and the first time the displayed frames
were *generated* rather than replayed.

**Authorization:** the user connected the iPad and granted explicit authority
for this session, covering both creating D-Bus sessions and sending bytes to
the device. The 2026-11-08 FED-LIVE-E001 grant was separate and already spent.

Private evidence: run `fedora-host-20261108T080007Z`, file index SHA-256
`669db3bf4578aff81d4a8bcd878cbc2706f18da8138414b9e79c65b41088de12`.

## What was proven

| Leg | Result |
| --- | --- |
| Pinned 1280×960 virtual monitor | **works** — caps negotiated at exactly that size |
| PipeWire capture → Pillow → libjpeg-turbo | **works** — SOF0 1280×960, image correct |
| Handshake against the device | **works** — third byte-identical confirmation |
| Generated frames shown on the iPad | **works** — user-confirmed |
| Inbound input captured and parsed | **works** — 1,540 records, zero malformed |
| Injection moving the Linux pointer | **works** — once the stream has a consumer |

## Stage A — the GNOME half, no device

**Fact.** `ScreenCast` version 4, `RemoteDesktop` version 1,
`SupportedDeviceTypes = 7`, as FED-DBUS-E001 recorded. The pinned-mode
`RecordVirtual` call created a virtual monitor and the GStreamer pipeline
negotiated:

```text
video/x-raw, width=(int)1280, height=(int)960, format=(string)RGB,
framerate=(fraction)0/1, max-framerate=(fraction)30/1,
colorimetry=(string)0:0:4:1, interlace-mode=(string)progressive
```

So the `modes` key does exactly what the XML claims: the stream is fixed at
1280×960 and non-resizable. Captured frames encoded to valid JPEGs with SOF0
1280×960, and the decoded image was the desktop wallpaper rendered on the new
monitor — correct colours, correct geometry, no shearing.

**Fact — `framerate=(fraction)0/1` means variable rate: Mutter produces a
buffer only when the screen is *damaged*.** An idle virtual monitor yields no
buffers at all. That is correct for a screen cast and wrong for a display, so
the host repeats its last frame when no new buffer arrives, and treats a
timeout as "nothing changed" rather than an error. Only never receiving a first
frame is a failure.

## Stage B — against the device

**Fact.** The handshake succeeded with client dimensions **2048 × 1536** and
the extra-data block giving `diff_jpeg = False` — byte-identical to both the
Windows capture and FED-LIVE-E001. That is now three independent confirmations.

**Fact.** 120 solid-colour frames (2,379,720 bytes) streamed in 3.97 s, exactly
30 fps; then live captured frames at ~372 KB each sustained **~26.5 fps, about
10 MB/s**, over several runs of 28–38 s each.

**Fact — the user confirmed black/dark-grey flashing appeared on the iPad
during a live run.** The frames were generated by `hashi_jpeg.encode_frame`
from `SolidColourSource`, not replayed, which is what makes this distinct from
FED-LIVE-E001.

A correction to an intermediate reading: a mid-session answer that the app
showed "a waiting/connect screen" was about its state *between* runs. The app
does enter display mode during a session — proven independently by the fact
that it reports touch coordinates in the host's own 1280×960 space.

## The real finding: absolute motion needs a stream consumer

**Fact, measured.** `NotifyPointerMotionAbsolute` on a virtual stream is
**silently discarded until something is consuming the PipeWire stream**, while
the D-Bus call still returns success. Mutter's idle timer makes this
measurable:

| Condition | 40 motion calls | Verdict |
| --- | --- | --- |
| No PipeWire consumer | idle 14,741 → **15,605 ms** (kept climbing) | dropped |
| Consumer attached | idle 20,683 → **21 ms** | landed |

The cause is the code FED-DBUS-E001 already quoted:
`meta_stream_virtual_transform_position` returns FALSE unless
`meta_stream_source_is_enabled` *and* the source has a `ClutterStageView`, and
`handle_notify_pointer_motion_absolute` then logs "Dropping early absolute
pointer motion" and completes the call successfully.

**The symptom is misleading, which is why it is worth recording.**
`NotifyPointerButton` takes no stream argument and performs no transform, so it
lands regardless. A host in this state therefore produces **clicks at a stale
pointer position with a pointer that never moves** — observed directly as text
being selected and windows behaving oddly. Nothing reports an error.

`hashi_gnome.VirtualDisplaySession.inject` now refuses while
`stream_consumed` is false, and `hashi_host` sets that flag only once the
capture source has actually produced a frame, which is the only available proof
that a consumer exists.

## The closing run

**Fact.** 30 seconds, live desktop capture outbound and injection inbound:

| Measure | Value |
| --- | --- |
| Frames sent | 900 (335,278,073 bytes) |
| Records received | **1,540** |
| Events injected | **1,540** (0 ignored, 0 withheld) |
| `field0` counts | 5 → 5 downs, 6 → 4 ups, 10 → 1,531 motions |
| Frames **captured** | **820** |
| Frames repeated | 81 |
| Final idle time | 25 ms |

**The decisive number is `captured = 820`.** Every earlier run captured 1 or 2
frames, because a static virtual monitor is never damaged. 820 real captures
means the monitor was being redrawn continuously — which only happens if the
pointer was actually moving across it. So the closed loop is established by the
system's own behaviour, not by inference:

> iPad touch → TLV record → `NotifyPointerMotionAbsolute` → pointer moves on the
> virtual monitor → damage → new PipeWire buffer → JPEG → back to the iPad.

## Bugs the first run found, all fixed

Every one of these was invisible to 249 passing unit tests, which is the point
worth keeping:

1. **`GLib.Variant("(a{sv})", (prebuilt,))` does not work.** PyGObject's
   format-string creator tries to iterate an already-built `a{sv}` variant as a
   Python dict and raises `KeyError: 0`. `GLib.Variant.new_tuple()` is correct.
2. **Teardown masked the real failure.** `close()` called `Stop` on a session
   that was never started, so the resulting "Session not started" replaced the
   original error. It now records teardown errors and returns them.
3. **Stopping both sessions in sequence fails.** Stopping the RemoteDesktop
   session destroys the ScreenCast session object, so the second `Stop` raises
   "Object does not exist at path …". Only one is stopped now.
4. **`appsink` had no `try_pull_sample`.** Its pull methods live in the
   `GstApp` namespace, which must be imported even though it is never
   referenced.
5. **A damage-only stream looked like a stall.** See Stage A.
6. **`DeviceID` must be discovered, never assumed.** The hard-coded `1` worked
   for one session and failed the next with usbmux `BADDEV (Number=2)`, because
   usbmuxd reassigns the id on every attach. `ListDevices` is now queried first,
   preferring a USB attachment with the iPad's product id.
7. **Injection before a consumer exists is a silent no-op**, as above.

**A correction to FED-DBUS-E001.** That report suggested asserting the pinned
geometry via `Stream.Parameters`. That is wrong for a virtual stream: observed,
the only key present is `mapping-id`. `set_stream_parameters` in
`meta-screen-cast-stream.c` has branches for monitor, area and window streams
and **none for virtual**, and it runs once in `initable_init` before the
monitor exists. The geometry assertion belongs on the negotiated PipeWire caps
instead, which is a stronger check anyway: the pipeline pins width and height,
so a wrong size fails negotiation outright.

## Limitations

- **One host, one device, one app version, one session each.** Nothing here is
  a stability claim.
- **Throughput is naive.** ~372 KB per frame at 30 fps is about 10 MB/s, and an
  unchanged screen is re-sent in full every frame. The protocol's `diff_jpeg`
  path exists for exactly this but is gated off by the device and was never
  observed, so it cannot be implemented. Not re-sending unchanged frames is the
  obvious next saving and was not attempted.
- **Still unexercised**, unchanged: multi-touch and the `ContactID` path,
  keyboard (`field0` 1/2), `field0` 16/17, reconfiguration, the TLV `0x70`
  subtype, and differential JPEG. `field0` 3, 4, 7, 8, 9 and 11–17 have still
  never been seen on the wire; only 5, 6 and 10 have.
- **The `is-platform` option was never set**, so every session raised a
  screen-sharing indicator. Whether setting it is preferable for a display host
  is untested.
- **usbmuxd dropped the device once** between runs, with the iPad still
  enumerated on USB (`05ac:12ab`) and `DeviceList` empty. It returned without
  intervention being recorded. Cause unknown; worth watching for.
