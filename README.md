# HASHI

**H**ost **A**dapter for **S**plashtop **H**ardware **I**nterop

[![check](https://github.com/ASPRNG-PRGMR/hashi/actions/workflows/check.yml/badge.svg)](https://github.com/ASPRNG-PRGMR/hashi/actions/workflows/check.yml)
[![License: MIT OR Apache-2.0](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](#license)
[![Status: alpha](https://img.shields.io/badge/status-alpha-orange.svg)](#project-status)

**Use an iPad as a real USB-tethered display for your Linux machine, with the
unmodified Splashtop Wired XDisplay app on the tablet and no proprietary
software on the host.**

Splashtop ships its wired XDisplay host for Windows and macOS only. HASHI is a
clean, independently written Linux host that speaks the same wire protocol, so
the stock iPad app treats a Linux box as a valid host — the way Samba lets Linux
speak SMB, or libimobiledevice lets it speak lockdownd.

HASHI (橋, *hashi*, "bridge") contains no Splashtop code, binaries or assets.
See [Legal and scope](#legal-and-scope).

---

## What works today

Confirmed on real hardware, end to end:

- The stock Splashtop iPad app completes HASHI's handshake and renders frames
  generated by Linux.
- The iPad is a genuine **extended** display — a userspace virtual monitor the
  GNOME desktop really extends onto — not a mirror and not a replay.
- **Touch input flows back**: touching the iPad moves the Linux pointer, with
  clicks and motion injected into the compositor.
- No kernel module, no `evdi`, no root.

The protocol itself is decoded and validated to the byte: the entire
host→device direction of a 130 MB reference capture is reproduced with an
identical SHA-256, and three independent implementations (Python, C++17, Rust)
agree on 65 byte vectors, 9 D-Bus payloads and 8 whole JPEG frames with zero
mismatches.

## Project status

**Alpha.** It works, and it has worked repeatedly — but it has been exercised on
one host configuration and one tablet, and several protocol paths are decoded
without ever having been seen on the wire.

| | |
|---|---|
| Protocol decode | **Validated** — byte-exact against a reference capture, cross-checked by three implementations |
| Python host | **Works end to end** — this is the implementation to use |
| C++ core | Scope-complete, 129 tests, byte-identical to Python — **never run live** |
| Rust core | Dependency-free, 45 tests, byte-identical to Python — protocol core only |
| Compositor support | **GNOME / Mutter on Wayland only** |
| Resolution | Fixed at **1280×960** |
| Input | Pointer motion and buttons work. Multi-touch, keyboard and Pencil are decoded but **never observed** |

See [Known issues](#known-issues) before filing a bug, and the
[project log](docs/project-log.md) for the full evidence trail.

## Requirements

**Host**

- Linux with **GNOME Shell on Wayland** (developed against GNOME 51 / Mutter 51
  on Fedora 45). Other compositors are not supported yet — see
  [the architecture notes](docs/linux-host-architecture.md).
- `usbmuxd` (udev-activated; nothing needs starting by hand)
- PipeWire
- Python 3.11+ with **PyGObject** and **Pillow**
- GStreamer with `pipewiresrc` (`gstreamer1-plugin-pipewire`)

On Fedora:

```sh
sudo dnf install usbmuxd python3-gobject python3-pillow \
                 gstreamer1-plugins-base gstreamer1-plugin-pipewire
```

**Tablet**

- An iPad running **Splashtop Wired XDisplay**, unmodified, from the App Store
- A USB cable (this is a wired protocol; nothing goes over the network)

**Optional, for the native builds**

`cmake`, a C++17 compiler, `libturbojpeg` (2.x or 3.x), `glib2`, `gstreamer`,
and `cargo` for the Rust core.

## Quick start

```sh
git clone https://github.com/ASPRNG-PRGMR/hashi.git
cd hashi

# Build whatever is present and run every offline check. Touches no device.
./hashi.sh

# Plug the iPad in, open Splashtop Wired XDisplay on it, then:
./hashi.sh devices          # confirm usbmuxd sees the tablet
./hashi.sh plan             # print exactly what a run would do; changes nothing
./hashi.sh run --allow-session
```

`--allow-session` is required and deliberate: a run sends bytes to the tablet
and creates a Mutter session, so a monitor appears on your desktop and a
screen-sharing indicator shows. Nothing contacts the device without it.

Useful flags:

| Flag | Effect |
|---|---|
| `--solid` | Stream solid colour frames with no virtual monitor and no input injection. Separates a transport fault from a capture one. |
| `--seconds N` | Stop after N seconds instead of running until interrupted. |
| `--fps N` | Target frame rate (default 30). |
| `--no-skip-unchanged` | Re-send every frame, even identical ones. |
| `--device-id N` | Skip discovery and use a specific usbmux device id. |

The same three commands exist for the C++ binary as `native-plan`,
`native-devices` and `native-run` — but that implementation has never been run
against a device. Use the Python host.

## How it works

```
                          iPad (USB)
                     Splashtop app, unmodified
                               │
                               ▼
                     usbmuxd (Unix socket)
          device discovery, Connect to port 6789 byte-swapped
                               │
                               ▼
                   HASHI host  (python/ · native/ · rust/)
        handshake · record framing · JPEG prelude · input decode
                        │                        ▲
       RecordVirtual    │                        │  type-7 records
       pinned 1280x960  ▼                        │  (absolute pixels)
              Mutter ScreenCast  ─────────────►  NotifyPointer*
              virtual monitor, cursor embedded   RemoteDesktop
                               │
                               ▼
                   PipeWire  ──►  GStreamer pipewiresrc
                               │
                               ▼
                 libjpeg-turbo, quality 80, 4:2:0
                 paced to 30 fps, unchanged frames skipped
                               │
                               ▼
              Frame reaches iPad's Splashtop renderer
```

The host asks Mutter for a virtual monitor over its `ScreenCast` D-Bus API,
pinned to 1280×960 so the stream cannot be resized under it. The desktop
genuinely extends onto that monitor; PipeWire hands the frames back, they are
JPEG-encoded to the exact parameters the protocol expects, and framed into the
records the tablet understands. Inbound records carry absolute pixel
coordinates, which go straight into Mutter's `RemoteDesktop` input injection.

Each Linux layer replaces a Windows one:

| Windows piece | Linux equivalent used here |
|---|---|
| Apple Mobile Device Service / Bonjour | `usbmuxd`, spoken directly over its Unix socket |
| `lci_iddcx.dll` (IddCx virtual display driver) | Mutter `ScreenCast.RecordVirtual` — userspace, no kernel module |
| `IndirectKmd` kernel component | none needed |
| Windows Display Manager | Mutter on Wayland |
| `SendInput` / `InjectTouchInput` | Mutter `RemoteDesktop.NotifyPointer*` (evdev button codes) |

## Known issues

| | |
|---|---|
| **Rearranging displays freezes the tablet** | Changing the monitor layout in GNOME Settings while HASHI is running leaves the iPad stuck on its last frame until the host is restarted. The arrangement is effectively fixed for the duration of a run. [#1](https://github.com/ASPRNG-PRGMR/hashi/issues/1) |
| **GNOME/Mutter only** | The virtual monitor relies on Mutter's private D-Bus APIs. KDE, wlroots and X11 are unsupported. |
| **Resolution is fixed at 1280×960** | The protocol's reconfiguration path is decoded but was never captured, so no resize is implemented rather than guessed. |
| **Pointer only** | Multi-touch, keyboard and Pencil input are decoded but have never been observed on the wire; only pointer down, up and motion are exercised. |
| **Motion is silently dropped without a stream consumer** | Mutter discards `NotifyPointerMotionAbsolute` while returning success if nothing is consuming the PipeWire stream. The host orders startup to avoid this; it is the single sharpest trap in the codebase. |

## Repository layout

```
python/     Reference implementation — the one that has run end to end
native/     C++17 port: protocol core, encoder, Mutter contracts, composed loop
rust/       Dependency-free Rust core (protocol and encoding logic)
docs/       Research record: protocol findings, validation reports, methodology
hashi.sh    Launcher: build, test, conformance, plan, run
```

## Development

```sh
./hashi.sh check            # everything: builds, three test suites, conformance
./hashi.sh test             # the three suites only
./hashi.sh conformance      # cross-implementation byte comparison
./hashi.sh clean            # remove both build trees
```

Each piece separately:

```sh
cd python && python3 -m unittest discover -s tests -t .   # 289 tests
cmake -S native -B native/build && cmake --build native/build -j
ctest --test-dir native/build                              # 129 tests
cd rust && cargo test --offline                            # 45 tests
python3 native/tools/conformance.py   # 65 vectors ×2, 9 variants, 8 frames
```

Nothing above touches a device, and CI runs all of it on every push.

**Why three implementations?** A test asserts what its author believed. An
independent implementation landing on the same bytes is evidence the *decode*
is right. The Rust core takes no crates for the same reason: three
implementations agreeing means nothing if they share the code that produces the
bytes. The conformance harness is given deliberate negative controls — quality
79 vs 80, JFIF density 121 vs 120 at equal length — so that a green run means
something.

### Evidence discipline

Every finding is classified:

- **Fact** — directly observed, or stated in official documentation.
- **Inference** — a logical conclusion from observed evidence.
- **Hypothesis** — a plausible explanation awaiting confirmation.

This is what keeps assumptions from quietly becoming "facts" as an
investigation proceeds, and it is why claims in this repository can be checked
rather than taken on trust.

## Legal and scope

HASHI is an **interoperability** project in the tradition of Samba, Wine and
libimobiledevice.

- No Splashtop software, binary, asset or proprietary specification is
  included, redistributed or depended upon.
- Findings derive from independent observation of a protocol on the wire,
  publicly documented Microsoft and Apple platform APIs, and standard Linux
  interfaces.
- No vendor table data, code or resource is transcribed. The JPEG parameters,
  for example, are rebuilt from published ISO/IEC 10918-1 Annex K tables.
- Raw captures, pairing records, frame dumps and vendor binaries are **never
  committed**. Only derived, described behaviour is published.
- HASHI is not affiliated with, endorsed by, or connected to Splashtop Inc.
  "Splashtop" and "XDisplay" are trademarks of their respective owners, used
  here only to identify the software HASHI interoperates with.

This is not a formal two-team clean room, and the project does not claim to be;
see the [devlog](docs/splashtop-xdisplay-reversing-devlog.md) for what the
separation actually was.
